# שלב 2ג — סנכרון העורך לענן

> **סטטוס: הושלם ✅** · חלק משלב 2 ([`PHASE2.md`](PHASE2.md)).

## מטרה
שבעל העסק יוכל לערוך את אותו תפריט מהמחשב במסעדה, מהנייד ומהבית — בלי לאבד שינויים ובלי ששני מכשירים ידרסו זה את זה. העורך ממשיך לעבוד גם בלי שרת ובלי חשבון (מצב מקומי, כמו היום).

## זרימות משתמש
1. **העלאת התפריט המקומי לענן** — מחובר ורואה „התפריט שמור רק במכשיר הזה” → „שמירה בענן” (לחיצה אחת). מכאן כל שינוי נשמר אוטומטית גם בשרת.
2. **פתיחת תפריט מהענן** — רשימת התפריטים בשרת → „פתיחה”. אם יש במכשיר תפריט מקומי שלא נשמר בענן — מוצג אישור לפני החלפה.
3. **עבודה מכמה מכשירים** — בטעינה ובחזרה ללשונית העורך בודק אם יש גרסה חדשה בשרת; אם אין שינויים מקומיים שלא נשלחו — הגרסה החדשה נטענת אוטומטית.
4. **התנגשות** — שינויים מקומיים *וגם* גרסה חדשה בשרת → חלון בחירה: „לטעון את הגרסה מהענן” / „לשמור את הגרסה שלי (לדרוס את הענן)” — שתי האפשרויות מפורשות, שום דבר לא נדרס בשקט.
5. **ניתוק** — „ניתוק מהענן” משאיר את התפריט במכשיר, בלי למחוק בשרת. „תפריט חדש”, „טעינת דוגמה” ו„ייבוא JSON” מנתקים אוטומטית — כדי שלא ידרסו בטעות את התפריט שבענן.
6. **צופה (viewer)** — יכול לפתוח תפריטים מהענן; שינויים שלו נשארים במכשיר ומוצגת הודעה „צפייה בלבד”.
7. **בלי רשת** — השינויים נשמרים במכשיר ומסומנים „ממתין לסנכרון”; נשלחים אוטומטית כשהחיבור חוזר (או בטעינה הבאה).

## API (חדש)
| Method | Path | תפקיד מינימלי | הערות |
|---|---|---|---|
| GET | `/api/menus` | viewer | רשימה בלי תוכן: `id, slug, title, draftVersion, updatedAt, updatedBy` |
| POST | `/api/menus` | editor | `{ menu, slug? }` → 201. ולידציית zod המשותפת (`src/core/schema.ts`). slug נגזר מהשם אם לא נשלח, עם סיומת ייחודית |
| GET | `/api/menus/:id` | viewer | מחזיר `ETag: "<draftVersion>"`; עם `If-None-Match` תואם → 304 (בדיקה זולה מכמה מכשירים) |
| PUT | `/api/menus/:id` | editor | גוף = התפריט. **חובה `If-Match: "<draftVersion>"`** (אחרת 428). גרסה לא תואמת → 409 `version_conflict` + פרטי הגרסה בשרת. עדכון אטומי: `UPDATE … WHERE id=$1 AND draft_version=$2` |
| DELETE | `/api/menus/:id` | owner | נרשם ביומן הביקורת |

- גודל בקשה: עד 12MB לנתיבי התפריט (תמונות מוטמעות כ־data URL עד שלב 2ה); 1MB בשאר ה־API.
- כל תשובות ה־API: `Cache-Control: no-store` (מידע פרטי לא נשמר במטמון הדפדפן/פרוקסי).
- יומן ביקורת: יצירה ומחיקה. שמירות טיוטה **לא** נרשמות ביומן (שמירה אוטומטית הייתה מציפה אותו); `updated_by`/`updated_at` בטבלה מספיקים.

## צד לקוח
- `src/api/menus.ts` — פונקציות מוקלדות לנתיבים.
- `src/store/cloudStore.ts` — מצב החיבור (`checking / noServer / signedOut / ready`), קישור התפריט המקומי לתפריט בענן (`menuai:cloud:v1` ב־localStorage: `menuId, version, dirty`), שליחה מושהית (1.5 שנ׳), בקשה אחת בכל רגע, ניסיון חוזר עם backoff, בדיקה בחזרה ללשונית.
- `src/editor/CloudSection.tsx` — מקטע „ענן” בלשונית פרסום + חיווי מצב בסרגל העליון (`aria-live`).
- דגל `dirty` נשמר במכשיר — שינוי שלא נשלח לא „נשכח” גם אם סוגרים את הדפדפן.

## אבטחה
- הרשאות בשרת בכל נתיב (`requireRole`), Origin-check קיים על כל בקשה משנה, rate limit (PUT: 120/דקה).
- ולידציה מלאה של התפריט בשרת; נשמר רק הפלט של zod (שדות לא מוכרים נזרקים).
- אין IDOR בין עסקים — התקנה אחת = עסק אחד (ראו PHASE2 §0); מזהי תפריט הם UUID ונבדקים בפורמט.
- **מגבלה ידועה:** תמונות מוטמעות נשמרות כ־data URL בתוך ה־JSON עד שלב 2ה (העלאות עם הסגר ו־ClamAV).

- שרת: הרשאות לכל תפקיד × נתיב, ולידציה, נעילה אופטימית (409/428), 304, slug ייחודי, מחיקה וביקורת, גודל בקשה.
- לקוח: לוגיקת הסנכרון (טעינה אוטומטית מול התנגשות, dirty, ניתוק) בבדיקות יחידה עם fetch מדומה.
- e2e: מקטע הענן מוצג נכון כשאין שרת (מצב מקומי) ועובר axe.
